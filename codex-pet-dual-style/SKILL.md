# Codex Pet Dual Style

## 目标

把一个或一批角色参考图稳定地转换为可并存、可安装、可分享的 Codex v2 宠物：

- 2D 版：保留原插画或 Q 版语言，同时针对桌面宠物尺寸简化和锐化。
- 3D 版：保留同一角色身份，转换为精致 Q 版 3D 游戏角色或 PVC 手办质感的二维渲染精灵。
- 两版分别拥有完整 11 行动画、独立 ID、独立包和完整 QA；不得用一个版本覆盖另一个版本。
- 批量生产时先批准风格样板，再逐角色执行完整质量门槛；抽检不能替代逐宠物验证。

本 Skill 负责双版本产品逻辑、角色身份锁、清晰度、批量流程、跨版本一致性和发布规则。图像生成、图集处理与 Codex v2 硬契约由 `$hatch-pet` 执行。

## 必须加载的依赖

开始任务后先完整读取并遵守：

```text
${CODEX_HOME:-$HOME/.codex}/skills/hatch-pet/SKILL.md
${CODEX_HOME:-$HOME/.codex}/skills/.system/imagegen/SKILL.md
```

- 使用 `$imagegen` 生成主形象、动作条带、方向锚点和修复条带。
- 使用 `$hatch-pet` 自带脚本完成准备、提取、注册、组装、透明边缘处理、预览、验证和打包。
- 运行 `$hatch-pet` 脚本前，按其要求调用 `load_workspace_dependencies`，只使用返回的 Python。
- 不直接调用图像 API、图像 CLI、临时绘图脚本或本地程序生成视觉内容。
- 程序可以做确定性的裁切、缩放、帧注册、透明化、逐帧镜像、图集组装和 QA 图生成，但不能替代缺失的 AI 视觉条带。
- 若本 Skill 与 `$hatch-pet` 的图集格式、透明处理、方向定义或验收门槛冲突，以 `$hatch-pet` 当前版本为准。

## 指令优先级

按以下顺序解释需求：

1. 当前环境的安全、授权与外部写入边界。
2. Codex v2 图集硬契约和 `$hatch-pet` 的确定性验收门槛。
3. 用户在当前任务中明确指定的身份、画风、动作、命名、安装和发布要求。
4. 已批准的角色身份锁、风格样板和行为配置。
5. 本 Skill 的批量默认值与案例经验。

用户偏好可以覆盖默认动作设计，但不能取消尺寸、透明、方向、结构和最终 QA。若用户要求与运行时行语义冲突，应解释实际映射并选择兼容实现，不要假装应用支持不存在的独立状态。

## 适用范围与边界

使用本 Skill：

- 从一张或多张角色图制作 2D、3D 或成对版本。
- 把已有 2D 宠物重制为更清晰的 3D 画风，同时保留旧版。
- 批量转换一组角色，并要求统一风格与逐件质量保证。
- 修复双版本中的待机、拖动、方向、边界、清晰度、命名、安装包或仓库结构。

不要使用本 Skill：

- 用户需要真正的三维网格、骨骼、材质工程、GLB、FBX 或游戏引擎 Rig。
- 只需编辑普通图片且不涉及 Codex 宠物图集。
- 只需制作一个普通单版本宠物且没有双风格或批量要求；此时直接使用 `$hatch-pet`。

## 交付定义

默认每个角色生成两个独立产品；用户只要求一种风格时只生成所需版本：

```text
dist/
├── <slug>-2d/
│   ├── pet.json
│   ├── spritesheet.webp
│   ├── contact-sheet.png
│   ├── look-directions.png
│   └── validation.json
└── <slug>-3d/
    ├── pet.json
    ├── spritesheet.webp
    ├── contact-sheet.png
    ├── look-directions.png
    └── validation.json
```

安装目录可以使用基础 ID 和 3D 后缀：

```text
${CODEX_HOME:-$HOME/.codex}/pets/<slug>/
${CODEX_HOME:-$HOME/.codex}/pets/<slug>-3d/
```

仓库目录必须显式带风格后缀，推荐 `<slug>-2d/` 与 `<slug>-3d/`。安装 ID 与仓库目录名可以不同，但每个 `pet.json` 必须与实际安装目录和显示名称保持一致。

## 开始前建立生产简报

为每个角色记录以下内容。能从参考图可靠判断的字段直接推断；会改变角色身份、动作含义或外部写入范围的缺失信息才需要询问用户。

```yaml
character_slug: ascii-or-latin-safe-id
display_name: 用户可见名称
nicknames: []
references:
  identity: []
  costume: []
  style_2d: []
  style_3d: []
variants: [2d, 3d]
identity_lock: path/to/identity-lock.md
behavior_profile:
  idle_eye_policy: both-open-default
  idle_motion: expressive-subtle
  drag_profile: default-locomotion
  drag_direction_map: default
style_profile:
  2d: reference-led-chibi
  3d: polished-chibi-game-toy
delivery:
  package_zip: true
  install_local: false
  publish_repo: false
```

规则：

- 内部 ID 使用小写拉丁字母、数字和连字符，至少含一个拉丁字母或数字。
- 显示名称、昵称和描述可以使用中文与 Unicode。
- 成对版本默认使用 `<slug>` 和 `<slug>-3d`，显示名称使用“原名”和“原名 3D”。
- 不要因临时昵称改变安装 ID；重命名时同步更新 ID、目录、`pet.json` 和分享包。
- 本地安装、删除旧宠物、远程执行、Git 推送和发布都必须由用户明确要求；单纯“制作”不代表这些权限。

## 最小可用输入：一张透明角色图

一张透明背景的卡通角色图足以完成整套生产，包括 2D、精致 Q 版 3D、9 组标准动画、16 向视线、透明图集、QA 预览和可分发包。用户不需要预先提供动作图、侧视图、背视图、命名表或提示词。

推荐的单图条件：

- PNG 或 WebP，带真实 alpha；透明区域不是画进图片里的棋盘格、白底或黑底。
- 只有一个角色，尽量是正面或轻微三分之四视角的完整全身图。
- 头顶、头发、耳朵、翅膀、尾巴、手、脚、裙摆和固定道具均未裁切。
- 没有文字、UI、场景、投影、地面阴影、漂浮特效或其他人物遮挡主体。
- 分辨率足以看清眼睛、嘴、发型、主要饰品、服装分区和左右非对称特征；长边约 512 像素以上更稳，但清晰的小图也可以进入主形象重建流程，不能仅因低于任意像素阈值拒绝。

透明参考图用于身份提取，不直接当作最终动画帧。后续仍按 `$hatch-pet` 使用该版本的主形象、布局参考和可清理色键背景生成动作条带，再确定性组装成透明图集。

### 单图缺失视角的处理

单图看不到的侧面与背面不阻塞生产，按以下规则保守推断：

- 可见事实优先：锁定正面能确认的轮廓、配色、眼睛、发型、饰品侧别、服装层级和固定道具。
- 不凭空新增身份级元素：不添加新徽记、文字、武器、翅膀、尾巴、首饰或第二套服装。
- 看不到的后侧结构采用与可见设计一致的最简单延伸；避免生成复杂的新花纹或强叙事细节。
- 已看见的非对称元素保持真实侧别；无法确认的隐藏细节默认不做新的非对称设计。
- 四基准方向阶段负责建立可读的上、右、下、左姿态，但不得声称推断出的背面细节与官方设定完全一致。
- 如果角色身份依赖不可见的背部图案、双面道具、特殊尾部、机械背包、多层翅膀或严格设定稿，才在大批量展开前请求相应侧视/背视参考。

### 用户只给一张图时的默认决策

当用户说“按这个 Skill 完整生产”且只提供图片时，不因以下信息缺失而暂停：

- 名称：优先从用户文字或文件名推断；仍无法判断时选择短、友好且可修改的显示名与安全 slug。
- 版本：本 Skill 默认生成可并存的 2D 和 3D 两版；用户明确只要一种时只做该版本。
- 2D 风格：跟随原图的卡通语言，并针对 `192x208` 做清晰度简化。
- 3D 风格：使用本 Skill 的“精致 Q 版 3D 游戏角色”默认值。批量任务先做一个样板；用户明确允许按默认方案直接生产时，不需要为每个角色重复等待风格确认。
- 动作：使用标准状态语义与高质量 humanoid 待机默认值；“后颈拎起”等专属拖动预设只有用户明确要求时才启用。
- 交付：生成成品目录、QA 文件和可分发包；不自动安装、覆盖、删除或上传。

以下信息不是启动所必需，但用户提供后应写入生产简报并覆盖默认值：正式名称与昵称、明确侧视/背视、批准的 3D 样板、待机表情、拖动动作、必须保留或禁止的细节、安装目标和发布位置。

## 角色身份锁

### 1. 先拆分三类特征

在生成任何动作前写 `identity-lock.md`，把特征分为：

- 不可变身份：头身比例、头部轮廓、发型轮廓、发色与眼色、主要服装块、标志性配色、非对称饰品所在侧、固定道具、角色年龄感和人格气质。
- 风格可变：线稿粗细、材质、光照、阴影方式、2D 或 3D 表现、微小蕾丝与纹理的简化程度。
- 动画可变：眨眼、微笑、低头、抬头、挥手、失败表情、身体倾斜、裙摆和发梢的运动。

不要把参考图中的瞬时表情误当成永久身份。例如参考图在眨单眼，不代表待机必须永远单眼闭合；当前用户对待机眼睛的明确要求优先。

### 2. 明确左右侧

对每个非对称特征同时记录：

- 角色自身的左侧或右侧。
- 正面图中位于画面 `screen-left` 或 `screen-right`。
- 侧脸、移动和方向动画中允许出现的遮挡关系。

不要只写“左边的发饰”。镜像会改变非对称头饰、服装、文字、徽记、持物手和光照含义；存在任何这类特征时，左右移动行必须分别生成。

### 3. 建立两套主形象

- 2D 与 3D 都从原始身份参考和同一身份锁出发。
- 2D 成品不能作为 3D 的唯一身份来源；3D 样板不能覆盖原始发型、服装或饰品事实。
- 每个版本各自生成并批准 `canonical-base.png`，后续所有该版本条带都必须附带其主形象。
- 两版允许材质和细节层级不同，但并排看时必须一眼认出是同一角色。

## 风格样板门槛

在以下情况下先只生成一张风格预览，不修改现有宠物、不安装、不批量展开：

- 首次把 2D 角色改成 3D 画风。
- 用户只描述了抽象风格，没有批准的视觉参考。
- 批量项目还没有统一的 2D 或 3D 样板。

预览通过后，把它记录为风格参考。用户已提供批准样板或明确要求直接生产时可以跳过等待，但仍要生成并批准该版本的主形象。

批量生产先选一个结构最复杂、非对称特征明显的代表角色做试产。只有以下内容通过，才把风格扩展到全批次：

- 角色身份准确。
- 原生 `192x208` 尺寸下五官、轮廓和主要饰品清晰。
- 2D 与 3D 的简化程度、材质和光照可稳定复现。
- 动作条带不会因长发、裙摆、翅膀或道具频繁贴边。

## 2D 风格规则

- 保留原画最有识别度的轮廓、配色、表情语言和服装分区。
- 减少在 `192x208` 中会塌成噪点的蕾丝、细线、发丝和半透明装饰。
- 加强眼睛、嘴、发饰、手势和外轮廓的明度或色相分离。
- 关键轮廓应比装饰线更粗；不要依赖极细描边维持身份。
- 不要把高分辨率插画直接缩小后当成宠物帧；必须为宠物尺寸重新设计。
- 如果界面截图显得模糊，先确认图集是否无损，再检查“高细节缩小后被 UI 放大”的问题。无损 WebP 不等于视觉清晰。

## 3D 风格规则

默认 3D 风格为“精致 Q 版 3D 游戏角色”：介于高品质手游角色渲染与 PVC 手办之间。

- 使用圆润、清楚、可读的头发块面和服装褶皱。
- 保留大眼、标志性发饰、主要配色与服装层级，不走写实皮肤或成人写实比例。
- 控制高光和材质噪声，避免小尺寸下形成糊边、塑料反光斑或细碎纹理。
- 用较大的材质块区分头发、皮肤、布料、金属和饰品。
- 立体感来自形体、光照和遮挡，不来自投影、地面阴影、光晕或场景。
- 3D 版仍是透明二维精灵图集；不要承诺或输出真实三维模型文件。

## Codex v2 图集硬契约

每个最终版本必须满足：

- `spriteVersionNumber: 2`。
- 8 列 × 11 行。
- 每格 `192x208`。
- 最终尺寸 `1536x2288`。
- PNG 或无损 WebP，RGBA 透明背景。
- 8×9、`1536x1872` 只允许作为中间图集，不能发布。
- v2 最终图集的 `(row 0, column 6)` 是专用 neutral/default look frame，不是第七个待机动画帧；它使用已批准的正面 neutral 或 idle 基准。`row 0, column 7` 仍须透明。
- 已用格非空；除专用 neutral 外的未用格完全透明；完全透明像素不得残留隐藏 RGB。按当前契约，最终 v2 图集共有 74 个已用格。

每个安装包的 `pet.json` 至少为：

```json
{
  "id": "character-id",
  "displayName": "Character Name",
  "description": "One short sentence.",
  "spriteVersionNumber": 2,
  "spritesheetPath": "spritesheet.webp"
}
```

昵称写入描述或用户指定的受支持字段，不要用多个目录 ID 表示同一安装项。缺少 `spriteVersionNumber: 2` 会让应用按 v1 读取并拒绝 2288 像素高的图集。

标准行动画契约：

| 行 | 状态 | 已用列 | 时长 |
| --- | --- | --- | --- |
| 0 | idle | 0-5；v2 的列 6 为 neutral | 280, 110, 110, 140, 140, 320 ms |
| 1 | running-right | 0-7 | 前 7 帧 120 ms，末帧 220 ms |
| 2 | running-left | 0-7 | 前 7 帧 120 ms，末帧 220 ms |
| 3 | waving | 0-3 | 前 3 帧 140 ms，末帧 280 ms |
| 4 | jumping | 0-4 | 前 4 帧 140 ms，末帧 280 ms |
| 5 | failed | 0-7 | 前 7 帧 140 ms，末帧 240 ms |
| 6 | waiting | 0-5 | 前 5 帧 150 ms，末帧 260 ms |
| 7 | running | 0-5 | 前 5 帧 120 ms，末帧 220 ms |
| 8 | review | 0-5 | 前 5 帧 150 ms，末帧 280 ms |
| 9 | look A | 0-7 | 000, 022.5, 045, 067.5, 090, 112.5, 135, 157.5 |
| 10 | look B | 0-7 | 180, 202.5, 225, 247.5, 270, 292.5, 315, 337.5 |

`000` 表示向上看，不是正面静止。neutral/default 使用 `row 0, column 6`；无方向输入由运行时回退到 neutral/idle 机制。

## 视觉任务图

每个版本最多包含 13 个视觉任务：

1. 一张主形象。
2. 九条标准动作行。
3. 一条四基准方向行：`000 up`、`090 screen-right`、`180 down`、`270 screen-left`。
4. 前半圈方向行 `000-157.5`。
5. 后半圈方向行 `180-337.5`。

依赖顺序：

```text
身份锁
  -> 风格样板批准
  -> 该版本主形象
  -> 标准动作行
  -> 标准动作 QA
  -> 视线机制说明
  -> 四基准方向
  -> 前半圈注册与 QA
  -> 后半圈注册与 QA
  -> 最终组装、一次性色键清理、完整 QA
  -> 打包
  -> 按授权安装或发布
```

禁止让图像模型直接生成或修复完整 8×11 图集。每个标准动作修复完整一行；每个最终方向修复完整半圈行。不要把单独生成的最终方向格混入另一轮生成的方向行。

视觉来源与落盘规则：

- 只有主形象任务可以在没有图片参考时从文字开始；每个动作条带都必须附带该版本的 `canonical-base.png`、任务清单列出的身份参考和对应布局参考。
- 布局参考只定义帧数、间距、中心和安全区；输出中出现参考格线、标签、背景色块或定位点即失败。
- 方向基准还要附带身份锁中所有决定脸型、眼睛、发型、非对称饰品和道具运动的图片。
- 前半圈附带已批准四基准；后半圈还要附带完成的前半圈作为尺度与接缝参考。
- 选中生成结果后，父任务把该原图复制到任务清单指定的 `decoded/` 路径，立即执行对应的逐行检查，再标记任务完成。只有返回路径、但未复制或未检查，不算完成。
- 每个视觉任务使用一个隔离生成任务，不在同一任务中连续生成多个主形象或动作行。

## 标准动作语义

- `idle`：安静、低干扰且有可见微动；首帧能作为静止图。
- `running-right` / `running-left`：应用拖动宠物时使用的移动视觉。默认是对应方向的移动；用户可以选择兼容的自定义拖动姿态。
- `waving`：通过手、爪、翅膀或肢体完成问候，不画挥手线。
- `jumping`：用身体高度表现起跳、峰值、下落和落定，不画地面和冲击特效。
- `failed`：清楚的失败、泄气或难过反应，不使用脱离身体的红叉和漂浮符号。
- `waiting`：等待用户批准、补充或帮助的询问姿态，与 idle、review 明显不同。
- `running`：Codex 正在工作、思考、扫描或处理，不是角色用脚奔跑。
- `review`：专注检查结果，不凭空新增放大镜、文件、代码或 UI。

各状态必须保持同一身份、同一固定道具和同一侧别。不要从其他状态复制 `waiting`、`running`、`failed`、`review`、`jumping` 或 `waving` 来冒充。

先生成并批准 `running-right`，再决定 `running-left`：

- 只有角色、服装、饰品、持物、标记和光照都完全适合翻转，且动作语义翻转后仍正确时，才使用 `$hatch-pet` 的逐帧镜像脚本。
- 镜像时保持原帧时间顺序；不能镜像整条长图，因为那会同时反转动作节拍。
- 任何非对称身份或方向特定的悬吊/倾斜规则都要求单独生成 `running-left`。

### 高质量 humanoid 待机默认值

仅在用户没有指定别的待机人格时，使用以下默认值：

- 6 帧包含轻微呼吸、很小的歪头与回正、手部微调、发梢/丝带/裙摆的延迟摆动。
- 首帧和末帧双眼睁开。
- 可以有一次双眼同步短眨；不要默认单眼长期闭合或连续眨眼。
- 所有动作保持低幅度，不得像挥手、工作、失败或跳跃。

这只是人形角色的质量默认值。原始角色以眨眼为核心设定或用户明确要求时可以改变。

### 可选的“后颈拎起”拖动预设

只有用户明确选择类似小猫后颈被拎起的动作时，应用 `scruff-suspend`：

- 看不见的悬点位于后颈或上衣领；不出现手、夹子、绳子或吊钩。
- 头部与悬点基本固定，肩部略微收拢，双脚全程离地。
- 不是单独踢腿；腰、胯、裙摆、大腿、双腿、鞋靴、长发和丝带作为有重量的下半身整体缓慢摆动，并带少量滞后。
- 循环必须闭合，末帧到首帧不能突然改变摆幅或倾角。
- 如果用户要求方向反作用：向右移动时下半身位于悬点的 `screen-left`，向左移动时位于 `screen-right`；8 帧都要保持主倾向，不得在首尾帧回到垂直或穿过中线。
- 如果用户明确要求所有拖动方向完全相同，可以让两条移动状态确定性复用同一条已经通过 QA 的完整行；一旦用户要求左右相反，必须分别生成或使用能保证侧别正确的确定性变换。
- 有非对称头饰、服装或光照时不要镜像；分别生成两行。

## 布局、背景与特效

- 条带使用与角色配色明显分离的纯色色键背景；颜色以 `pet_request.json` 为准，不固定使用绿色。
- 每个姿势必须完整、分离、居中并留有安全边距；不能跨槽、贴外画布、互相遮挡或把相邻角色碎片带入本格。
- 不要生成可见格线、标签、角度、帧号、箭头、棋盘格或布局参考色。
- 不要生成文字、UI、场景、地板、投影、落地阴影、光晕、模糊、速度线、动作弧、尘土、落地痕、漂浮星星或脱离身体的特效。
- 允许的状态特效必须与身体接触、位于同一连通精灵内、硬边且不接近色键颜色。
- 长发、裙摆、翅膀、尾巴和道具是边界高风险项；生成提示中预留额外安全区，QA 时逐格查看四边。

## 提取与串格规则

默认使用组件提取，不要为了少数失败行把全部标准行改成固定槽切割。

- 源条带中姿势分离且组件可识别：使用自动组件提取。
- 只有自动组件提取失败、但源条带的槽位、比例和基线肉眼稳定时，才对该行启用 `stable-slots`。
- 使用 `stable-slots` 后必须查看 GIF 和高对比背景上的每个单格，确认没有相邻角色的发梢、裙摆、鞋、阴影或边角串入。
- 如果固定槽保留了相邻姿势碎片，恢复组件提取或重制该行并扩大槽间色键间隔；不要全局继续使用固定槽。
- 提取问题是确定性故障时先修提取，不要重画视觉正确的动作。
- 源图本身跨槽、重叠、裁切或缺帧时重制完整动作行；程序裁切不能掩盖坏源图。

## 16 向视线规则

### 视线机制说明

标准动作通过后写 `qa/look-mechanics.md`：

- 哪个部位固定：脚底、骨盆、躯干或其他自然基座。
- 哪个部位先动：眼球、瞳孔、眼睑、头、颈、面板或触角。
- 哪些部位跟随：头发、耳朵、丝带、上身和道具。
- 每个基准方向露出哪一侧，哪些特征被遮挡。
- 非对称饰品、持物和服装如何保持真实侧别。
- 每 22.5° 的动作预算；相邻格不得突然大幅弯曲、缩放或横移。

人形角色默认由眼睛和眼睑先引导，头颈与上身小幅跟随。不要用大范围栅格扭曲拉长头骨、眉眼、嘴、手或衣服；不要让头动而眼睛始终锁死在同一表情。

### 四基准方向

先生成同一条四姿势基准行并批准：

```text
000 = up
090 = screen-right
180 = down
270 = screen-left
```

- 左右是观看者/屏幕坐标，不是角色自身坐标。
- 面部角色用鼻尖、瞳孔、眼睑和头部中心判断。
- `090` 与 `270` 必须明显相反；`000` 与 `180` 必须明显相反。
- 任一基准含糊都不能继续。可单独重制失败的基准锚点，再确定性重组成批准基准条。

### 两条连续方向行

- 前半圈必须从批准基准条生成，并形成一套连续的 8 姿势家族。
- 前半圈注册、边缘、语义和连续性通过后，才能生成后半圈。
- 后半圈同时参考批准基准条和已完成前半圈，以约束 `157.5 -> 180` 与 `337.5 -> 000` 两个接缝。
- 不要逐格独立生成、镜像或重新居中；不要通过整体旋转、倾斜或仿射变换伪造视线。
- 四个基准必须明确；中间角度允许线索柔和，但不能落入错误象限、反向或破坏连续循环。

### 人形方向收敛策略

如果方向正确但轮廓、体高或脚底跳动，说明生成器在重画全身：

1. 冻结身体、服装、脚底锚点、体高和头部尺寸。
2. 主要改变眼球/瞳孔、眼睑、眉、头颈和少量发梢。
3. 用已通过的相邻行作为共享尺度与注册参考。
4. 不要把整行统一缩小一个百分比来换留白；这常会造成两半圈比例断裂。优先收拢发梢、丝带和外伸肢体。

如果左右或上下语义相反，先修方向定义，不要把它当成几何问题：

- 左右：明确鼻尖与瞳孔相对头中心的 `screen-left/screen-right` 推进。
- 上下：明确向上时视线靠眼眶上缘，向下时靠眼眶下缘，同时配合眼睑和头颈。

## 透明与色键

- 中间接触表中的细色键边缘不是标准动作阶段的视觉失败；最终透明结果才是判据。
- 完成 11 行组装后只运行一次 `$hatch-pet` 的边缘色键清理，标准 8×9 中间图集不单独清理。
- 清理必须保持 alpha，清空全透明像素下的 RGB，并输出报告。
- 最终清理报告 `ok: true` 且 `validate_atlas.py --require-v2` 通过后，不再凭肉眼猜测色边、反复加清理脚本或重新生成动作。
- 若确定性透明或结构验证失败，按流水线故障处理，不能用图像重试掩盖。
- 角色实体内部出现意外的全透明横条、接缝、孔洞或切片边界属于硬失败；在高对比背景或 alpha mask 上检查。

## 清晰度验收

每个版本都必须在以下视图检查：

- 原生 `192x208` 单格。
- 接近应用显示的正常尺寸。
- 模拟约 1.25-1.5 倍 UI 放大的视图，用常见平滑缩放检查边缘是否发虚。

检查眼睛、嘴、发饰、手、鞋、外轮廓和动作意图。若文件是无损 WebP 但仍显糊，优先减少微小细节、加粗关键轮廓、提高五官对比和减少半透明细边；不要把问题误判为压缩并重复保存。

## QA 门槛

### A. 确定性硬门槛

每个版本都必须满足：

- 最终图集 `1536x2288`、RGBA、8×11、单格 `192x208`。
- `pet.json` 含 `spriteVersionNumber: 2` 并指向真实文件。
- 精确帧数、74 个已用格非空、专用 neutral 存在，其余未用格全透明。
- 无不透明色键、隐藏 RGB、边缘裁切、槽位重叠和意外透明孔洞。
- `qa/review.json` 无错误。
- `qa/chroma-despill-extended.json` 为 `ok: true`。
- `final/validation-extended.json` 为 `ok: true`，错误与不可接受警告为空。

### B. 标准动作视觉硬门槛

- 9 行身份、画风、色彩、头身比、饰品侧别和固定道具一致。
- 每行动作语义正确，循环完整，无反向节拍、首尾跳变、基线跳动、比例跳动或视觉静止。
- idle 与 waiting、running、review、failed 明显不同。
- 没有串格边角、白底、阴影、特效残片或其他角色。
- 自定义拖动预设必须按生产简报逐帧满足悬点、倾斜和方向映射。
- 生成并人工查看标准接触表与每行 GIF。

### C. 方向硬门槛

- 四基准方向无标签也能辨认。
- 16 个方向固定顺时针排列，并与 neutral 明显不同。
- 每个方向在 `qa/direction-semantics.json` 中包含 `verdict`、`expected`、`observed` 和 `reason`。
- 对角方向同时记录水平与垂直证据。
- 三个互相隔离的盲测者只看随机 A/B 轴向图；四基准对必须严格多数通过。
- 中间角度盲测含糊可以是警告，但标注视图不得出现错误象限或循环反转。
- `qa/look-continuity.json` 中的指标警告必须与正常尺寸动画一起复核；只有肉眼可见的跳位、缩放、身份变化或语义断裂才是连续性硬失败。
- 修复后的方向必须由独立 QA 者或用户复核，不能由修复执行者单独批准。

### D. 跨版本硬门槛

把 2D 与 3D 的 neutral、四基准和代表动作并排查看：

- 必须识别为同一角色，而不是只共享粉色、服装类型或泛化五官。
- 发型轮廓、眼色、主要饰品侧别、服装分区和固定道具保持一致。
- 3D 可以简化线条和纹理，但不能改变角色年龄感、人格气质或标志性比例。
- 2D 与 3D 的 ID、显示名称、安装目录和分享包互不覆盖。

### E. 发布硬门槛

- 每个版本的分享目录至少包含 `pet.json` 和 `spritesheet.webp`。
- 推荐同时包含接触表、方向图和验证报告，方便第三方审查。
- ZIP 创建后测试可列出和解压，文件哈希与批准成品一致。
- 安装后核对安装目录与交付包哈希；界面未刷新时提示重启或重新打开宠物列表。
- 发布到 Git 仓库前，只提交成品目录和必要文档；不得提交 `work/`、生成提示、会话数据库、鉴权信息、Base64、缓存或本机配置。

## 故障分类与修复顺序

每次失败先归类，再选择最小可发布修复范围：

| 类别 | 证据 | 优先修复 |
| --- | --- | --- |
| 身份/画风 | 变脸、饰品翻侧、材质漂移 | 重制完整动作行并加强身份锁 |
| 动作语义 | 状态不对、拖动方向错误 | 重写动作机制并重制完整动作行 |
| 源图边界 | 跨槽、贴边、重叠、缺帧 | 重制完整动作行，增加留白与间隔 |
| 组件/提取 | 源图正确但自动分割失败 | 调整该行提取；必要时批准 stable-slots |
| 色键/透明 | 透明边缘或隐藏 RGB 失败 | 只用确定性色键流水线修复 |
| 方向语义 | 左右/上下反向、基准含糊 | 修基准定义；重制失败的完整方向行 |
| 连续性 | 脚底、面积、中心、比例跳变 | 共享尺度、冻结身体、重制完整方向行 |
| 清晰度 | 原生或放大视图发虚 | 简化细节、加粗轮廓、提高对比后重制行或版本 |
| 传输/代理 | 网络错误、无输出、会话卡死 | 重试同一规范或替换隔离任务，不降低 QA |

修复规则：

1. 确定性故障先用确定性修复；视觉源图错误才重新生成。
2. 标准动画修完整一行；方向动画修完整半圈行；不重做整个宠物，也不拼接单个新方向格。
3. 保存已经通过的身份、语义、尺度和边界属性；新结果必须与上一版对比。
4. 修复只有在减少失败数量或严重度且不破坏既有通过项时才算进展。
5. 同一根因连续出现两次，停止微调同类提示词，改变策略：冻结更多身体、强化四基准、简化外伸结构、改变提取方法或重新设计动作。
6. 修复只是把问题从一个格移到另一个格，视为循环，立即改变策略。
7. 网络失败没有生成图片时属于传输重试，不得降低模型、画风或 QA 标准，也不得标记任务完成。
8. 子任务长时间无响应时中断并用新隔离任务重试；保留已通过产物，不从头重来。

## 批量生产

### 批次策略

- 先完成一个最难代表角色的 2D/3D 试产并批准风格锁。
- 每个角色、每个版本使用独立运行目录、主形象、任务清单和 QA 报告。
- 共享的是模板、风格规范和质量门槛，不共享会导致身份污染的主形象或动作条带。
- 按 `$hatch-pet` 的依赖图并发，最多保持三个独立视觉生成任务；依赖未满足的任务不能提前生成。
- 任何未通过项目进入隔离修复队列，不得进入最终包；其他互不依赖项目可以继续。
- 每件宠物都跑完整确定性验证、标准动画预览、16 向语义、三路基准盲测和独立最终视觉 QA。不能只抽样检查一部分角色。
- 生成任务只返回选中源文件路径和一句 QA 说明，不返回 Base64 或额外图片附件。父任务只查看必要的最终接触表与问题图，不把每张生成图重复载入主会话。
- 选中图复制到运行目录并校验后，按 `$hatch-pet` 规则删除 `generated_images` 下可安全删除的原副本，控制批量磁盘与会话体积。

### 批次进度表

保持一个可见矩阵，每次只把真实存在且通过门槛的阶段标为完成：

| 角色 | 身份锁 | 2D 样板 | 2D 动作 | 2D 方向 | 2D QA | 3D 样板 | 3D 动作 | 3D 方向 | 3D QA | 配对 QA | 打包 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

建议阶段顺序：

1. 准备角色与身份锁。
2. 批准 2D/3D 主形象。
3. 生成并验证标准动作。
4. 生成并验证方向动作。
5. 完成每版与跨版本 QA。
6. 打包，并按用户授权安装或发布。

正常单版本可参考 `$hatch-pet` 的 30 分钟计划目标；双版本和批量按依赖与修复量扩展。时间目标不能取消任何硬门槛。

## 子任务、远程执行与取消

- 按 `$hatch-pet` 使用轻量隔离任务处理单个视觉生成、三份独立方向盲测和最终视觉 QA；父任务负责身份锁、清单、文件复制、确定性脚本、打包和外部写入。
- 盲测者不能看到角度标签、答案、提示词或其他盲测结果。
- 默认本机执行。只有用户明确指定远程主机、账户和执行范围时才使用远程 Codex。
- 远程返回的产物不能直接发布；同步回本地后仍执行完整确定性与视觉 QA。
- 远程网络或模型不可用时报告真实阻塞，不要伪造进度或悄悄换模型。
- 用户要求停止远程任务时，停止守护进程、子进程和相关自动监控；保留本地已存在成品，除非用户同时要求删除。

## 安装、重命名、删除与发布

- “制作”“打包”“安装”“覆盖”“删除”“上传”是不同权限，不得互相推断。
- 安装前核对目标 ID 是否冲突。成对版本必须作为两个独立宠物并存。
- 覆盖已有版本前确认是修复同一 ID；不要把 3D 覆盖到 2D ID。
- 重命名时更新显示名称、ID、目录、描述和分享包；图集视觉没有变化时不要重制。
- 删除旧名称或备份必须由用户明确要求。删除后说明删除内容以及是否可恢复。
- 推送仓库前先查看远端与本地状态、确认分支、检查提交清单；未经用户要求不要创建提交或推送。
- 推荐仓库结构使用 `<slug>-2d/` 与 `<slug>-3d/`，每个目录自包含，不依赖另一个目录。

## 保留与清理

每个已批准版本至少保留：

- `pet_request.json` 或等价生产简报。

## 从 Elysia 试产中固化的质量规则

以下规则是可复用的故障经验，不是所有角色的强制美术偏好：

- 参考图的单眼眨眼属于表情，不应自动锁成所有待机帧；待机眼睛策略必须单独记录。
- 非对称玫瑰头饰使左右镜像不安全；任何角色的非对称标志都必须先做侧别审计。
- 把所有行强制切成固定槽会引入相邻角色边角；提取方法必须逐行选择。
- `157.5 -> 180` 与 `337.5 -> 000` 是最容易出现尺度和中心跳变的两个方向接缝，必须单独验收。
- 方向几何通过不代表语义通过；左右、上下反向只有无标签盲测能可靠暴露。
- 为解决贴边而把整行统一缩小，可能制造更严重的跨行比例跳变；优先保持共享体高和脚底锚点，只收拢外伸部件。
- 角色在无损 WebP 中仍可能显糊；真正原因往往是细节过多的 192×208 精灵被 UI 放大。
- 拖动动作必须写成可验证的身体机制和屏幕方向映射，不能只写“像被拎起”或“左右晃动”。
- 用户后续修订的动作语义覆盖早期默认值；每次修订后重跑受影响行、完整图集和安装包 QA，不能只换一张图。
